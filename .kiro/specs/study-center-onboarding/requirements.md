# Requirements Document

## Introduction

The Study Center Onboarding feature covers the full lifecycle of bringing a new study center onto the platform via a sales-generated invite link. A `sales_admin` user generates a time-limited, token-gated invite link pre-attached to one or more universities from their branch's allowed list. A prospective study center operator opens the link, completes a public registration form, and the resulting record progresses through a multi-stage verification pipeline: document review by the responsible department or sub-department, then authorisation fee verification by finance, before the study center is activated and granted access to the student enrollment portal for its allocated programs.

## Glossary

- **System**: The study center onboarding application
- **Sales_Admin**: A user with the `sales_admin` role, scoped to a branch, responsible for generating invite links and owning the resulting study center
- **Invite_Link**: A unique, time-limited, token-gated URL generated by a Sales_Admin that allows a prospective study center operator to complete registration
- **Invite_Token**: The cryptographically unique token embedded in an Invite_Link, with a configurable expiry (default 7 days)
- **Study_Center**: A partner center record created via the onboarding flow, progressing through statuses: `pending_verification` → `pending_payment` → `active`
- **Ops_Admin**: A user with the `ops_admin` role, scoped to a department or sub-department, responsible for document verification and program allocation
- **Ops_Sub_Admin**: A user with the `ops_sub_admin` role, scoped to a sub-department, responsible for document verification and program allocation within that sub-department
- **Finance_Admin**: A user with the `finance_admin` role, responsible for configuring authorisation fees per university and verifying payment
- **UniversityAuthFee**: A configuration record associating a per-university authorisation fee amount, set by Finance_Admin
- **Program_Allocation**: A record linking a specific Program to a Study_Center, granting the center permission to enroll students into that program
- **Branch**: An organisational branch with a `salesDeptId` and `branchManagerId`, scoping which universities a Sales_Admin can access
- **University**: An academic institution with `allowedBranchIds` (branches permitted to use it) and `subDepartmentId` (the dept/sub-dept responsible for verification)
- **Registration_Form**: The public, token-gated form a prospective study center operator fills out to complete onboarding

## Requirements

### Requirement 1: Branch-Scoped University Visibility for Sales Admin

**User Story:** As a Sales_Admin, I want to see only the universities allocated to my branch, so that I can only generate invite links for universities my branch is authorised to work with.

#### Acceptance Criteria

1. WHEN a Sales_Admin requests the list of universities, THE System SHALL return only universities where the Sales_Admin's `branchId` is present in the university's `allowedBranchIds` array.
2. WHILE a university's `allowedBranchIds` array does not contain the Sales_Admin's `branchId`, THE System SHALL exclude that university from the Sales_Admin's university listing.
3. IF a Sales_Admin attempts to attach a university not in their branch's allowed list to an invite, THEN THE System SHALL return a 403 Forbidden response.
4. THE System SHALL scope all university queries for a Sales_Admin to the same `organizationId` as the Sales_Admin.

### Requirement 2: Invite Link Generation

**User Story:** As a Sales_Admin, I want to generate a time-limited invite link pre-attached to one or more universities, so that a prospective study center operator can register and be associated with those universities from the start.

#### Acceptance Criteria

1. WHEN a Sales_Admin generates an invite link, THE System SHALL require at least one university to be selected from the Sales_Admin's branch-allowed university list.
2. WHEN a Sales_Admin generates an invite link with at least one valid university selected, THE System SHALL create an Invite_Token with a default expiry of 7 days from creation.
3. THE System SHALL generate a cryptographically unique Invite_Token for each invite link creation request.
4. THE System SHALL record the Sales_Admin's user ID as the `referredBy` owner on the Invite_Token at creation time.
5. WHEN an Invite_Token is created, THE System SHALL return the full Invite_Link URL containing the token to the Sales_Admin.
6. IF a Sales_Admin submits an invite link generation request with no universities selected, THEN THE System SHALL return a validation error indicating at least one university is required.
7. IF a Sales_Admin submits an invite link generation request with a university ID not in their branch's allowed list, THEN THE System SHALL return a 403 Forbidden response.
8. THE System SHALL allow a Sales_Admin to view all Invite_Tokens they have generated, including their status (`pending`, `used`, `expired`) and expiry date.

### Requirement 3: Invite Token Expiry and Validation

**User Story:** As the System, I want to enforce invite token expiry and single-use semantics, so that invite links cannot be reused or accessed after they expire.

#### Acceptance Criteria

1. WHEN a prospective operator opens an invite link, THE System SHALL validate that the Invite_Token exists and has not expired.
2. IF a prospective operator opens an invite link with an expired Invite_Token, THEN THE System SHALL return an error indicating the link has expired and SHALL NOT render the registration form.
3. IF a prospective operator opens an invite link with a token that has already been used, THEN THE System SHALL return an error indicating the link has already been used and SHALL NOT render the registration form.
4. WHEN a Study_Center registration is successfully submitted via an invite link, THE System SHALL mark the Invite_Token status as `used` and SHALL NOT allow further registrations using that token.
5. THE System SHALL run a scheduled process that transitions all Invite_Tokens past their expiry date to `expired` status.

### Requirement 4: Public Registration Form Submission

**User Story:** As a prospective study center operator, I want to complete a registration form via the invite link without needing an account, so that I can submit my center's details and documents for review.

#### Acceptance Criteria

1. WHEN a prospective operator opens a valid invite link, THE System SHALL render the registration form without requiring authentication.
2. THE System SHALL display only the universities attached to the Invite_Token on the registration form's university selection field.
3. WHEN a prospective operator submits the registration form, THE System SHALL require the following fields: center name, center code, address, contact number, email address, and at least one document upload.
4. WHEN a prospective operator submits the registration form, THE System SHALL require the operator to select at least one university from the universities attached to the Invite_Token.
5. IF a prospective operator submits the registration form with any required field missing, THEN THE System SHALL return a validation error identifying each missing field.
6. IF a prospective operator submits the registration form with a center code that already exists in the organisation, THEN THE System SHALL return a validation error indicating the code is already taken.
7. WHEN a valid registration form is submitted, THE System SHALL create a Study_Center record with status `pending_verification`, linked to the Invite_Token's `referredBy` Sales_Admin as `referredBy`, and associated with the selected universities.
8. WHEN a Study_Center record is created, THE System SHALL record the submitted documents on the Study_Center record for subsequent review.
9. WHEN a Study_Center record is created, THE System SHALL notify the responsible Ops_Admin or Ops_Sub_Admin (determined by the university's `subDepartmentId`) that a new center is pending document verification.

### Requirement 5: Document Verification by Ops Admin / Ops Sub Admin

**User Story:** As an Ops_Admin or Ops_Sub_Admin, I want to review the submitted documents for a pending study center and approve or reject the application, so that only legitimate centers proceed to payment verification.

#### Acceptance Criteria

1. WHEN a Study_Center has status `pending_verification`, THE System SHALL make it visible to the Ops_Admin or Ops_Sub_Admin whose department or sub-department matches the `subDepartmentId` of any university associated with the Study_Center.
2. WHEN an Ops_Admin or Ops_Sub_Admin approves a Study_Center in `pending_verification` status, THE System SHALL transition the Study_Center status to `pending_payment`.
3. WHEN an Ops_Admin or Ops_Sub_Admin rejects a Study_Center in `pending_verification` status, THE System SHALL require a non-empty remarks field and transition the Study_Center status to `rejected`.
4. IF an Ops_Admin or Ops_Sub_Admin attempts to approve or reject a Study_Center not in `pending_verification` status, THEN THE System SHALL return an error indicating the action is not permitted at the current stage.
5. THE System SHALL record the reviewing user's ID, decision, remarks (if any), and timestamp on the Study_Center record when a document verification decision is made.
6. WHEN a Study_Center is approved by Ops_Admin or Ops_Sub_Admin, THE System SHALL notify the Finance_Admin that a new center is pending authorisation fee verification.
7. IF a user without the `ops_admin` or `ops_sub_admin` role attempts to perform document verification, THEN THE System SHALL return a 403 Forbidden response.

### Requirement 6: Authorisation Fee Configuration by Finance

**User Story:** As a Finance_Admin, I want to configure the authorisation fee amount per university, so that the correct fee is enforced when verifying payment for each study center.

#### Acceptance Criteria

1. WHEN a Finance_Admin creates or updates a UniversityAuthFee for a university, THE System SHALL accept a fee amount greater than zero.
2. IF a Finance_Admin submits a UniversityAuthFee with a zero or negative amount, THEN THE System SHALL return a validation error.
3. THE System SHALL allow only one active UniversityAuthFee record per university at any time.
4. WHEN a Finance_Admin updates a UniversityAuthFee, THE System SHALL replace the previous fee amount and record the update timestamp and Finance_Admin user ID.
5. THE System SHALL make the configured UniversityAuthFee amount visible to Finance_Admin users when reviewing a Study_Center pending payment.

### Requirement 7: Finance Authorisation Fee Verification

**User Story:** As a Finance_Admin, I want to verify that the authorisation fee has been paid for a study center, so that only centers that have paid can be activated.

#### Acceptance Criteria

1. WHEN a Study_Center has status `pending_payment`, THE System SHALL make it visible to Finance_Admin users along with the applicable UniversityAuthFee amount for each associated university.
2. WHEN a Finance_Admin approves a Study_Center in `pending_payment` status, THE System SHALL transition the Study_Center status to `active`.
3. WHEN a Finance_Admin rejects a Study_Center in `pending_payment` status, THE System SHALL require a non-empty remarks field and transition the Study_Center status to `rejected`.
4. IF a Finance_Admin attempts to approve or reject a Study_Center not in `pending_payment` status, THEN THE System SHALL return an error indicating the action is not permitted at the current stage.
5. THE System SHALL record the Finance_Admin user ID, decision, remarks (if any), and timestamp on the Study_Center record when a payment verification decision is made.
6. IF a Finance_Admin attempts to approve a Study_Center for a university with no configured UniversityAuthFee, THEN THE System SHALL return an error indicating the authorisation fee has not been configured for that university.
7. IF a user without the `finance_admin` role attempts to perform payment verification, THEN THE System SHALL return a 403 Forbidden response.

### Requirement 8: Study Center Activation and Portal Access

**User Story:** As a study center operator, I want my center to be activated after finance approval, so that I can log in and access the student enrollment portal.

#### Acceptance Criteria

1. WHEN a Study_Center status transitions to `active`, THE System SHALL generate login credentials for the study center and store them on the Study_Center record.
2. WHEN a Study_Center is activated, THE System SHALL send the login credentials to the email address provided during registration.
3. WHILE a Study_Center status is not `active`, THE System SHALL deny login attempts using that center's credentials with an appropriate error message.
4. WHEN an active Study_Center operator logs in, THE System SHALL grant access only to the student enrollment portal and SHALL NOT grant access to internal staff dashboards.
5. THE System SHALL allow a Study_Center operator to view their own Study_Center record, including status and associated universities.

### Requirement 9: Program Allocation by Ops Admin / Ops Sub Admin

**User Story:** As an Ops_Admin or Ops_Sub_Admin, I want to allocate specific programs to an active study center, so that the center can only enroll students into the programs I have authorised.

#### Acceptance Criteria

1. WHEN an Ops_Admin or Ops_Sub_Admin creates a Program_Allocation for a Study_Center, THE System SHALL require a valid program ID and a valid study center ID with status `active`.
2. IF an Ops_Admin or Ops_Sub_Admin attempts to allocate a program to a Study_Center that is not `active`, THEN THE System SHALL return an error indicating the center must be active before programs can be allocated.
3. THE System SHALL allow an Ops_Admin or Ops_Sub_Admin to allocate multiple programs to a single Study_Center.
4. THE System SHALL prevent duplicate Program_Allocation records for the same program and study center combination.
5. IF an Ops_Admin or Ops_Sub_Admin attempts to create a duplicate Program_Allocation, THEN THE System SHALL return a validation error indicating the program is already allocated to that center.
6. WHEN an Ops_Admin or Ops_Sub_Admin removes a Program_Allocation, THE System SHALL prevent new student enrollments for that program at that center but SHALL NOT affect existing enrollments.
7. THE System SHALL scope program allocation actions to the Ops_Admin or Ops_Sub_Admin's own department or sub-department.
8. IF a user without the `ops_admin` or `ops_sub_admin` role attempts to manage program allocations, THEN THE System SHALL return a 403 Forbidden response.

### Requirement 10: Study Center Enrollment Scope Enforcement

**User Story:** As the System, I want to enforce that a study center can only enroll students into its allocated programs, so that unauthorized enrollments are prevented.

#### Acceptance Criteria

1. WHEN a Study_Center operator initiates a student enrollment, THE System SHALL verify that a Program_Allocation exists for the requested program and that study center.
2. IF a Study_Center operator attempts to enroll a student into a program with no Program_Allocation for that center, THEN THE System SHALL return a 403 Forbidden response.
3. WHEN a Study_Center operator queries available programs for enrollment, THE System SHALL return only programs with an active Program_Allocation for that center.

### Requirement 11: Onboarding Status State Machine and Audit History

**User Story:** As a system operator, I want study center onboarding status to follow a strict, auditable progression, so that no stage can be skipped and the workflow remains consistent.

#### Acceptance Criteria

1. THE System SHALL enforce the following valid status transitions for a Study_Center during onboarding:
   - `pending_verification` → `pending_payment` (on Ops_Admin or Ops_Sub_Admin document approval)
   - `pending_verification` → `rejected` (on Ops_Admin or Ops_Sub_Admin document rejection)
   - `pending_payment` → `active` (on Finance_Admin payment approval)
   - `pending_payment` → `rejected` (on Finance_Admin payment rejection)
2. IF a status transition is attempted that is not in the valid set, THEN THE System SHALL return an error and leave the Study_Center status unchanged.
3. THE System SHALL record a status history entry on the Study_Center each time the status changes, including the new status, actor user ID, remarks (if any), and timestamp.
4. THE System SHALL preserve all status history entries and SHALL NOT allow deletion or modification of existing history entries.
